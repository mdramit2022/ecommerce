# Go-Live Audit - 2026-09-15

> Verdict: **Not ready to go live**. 66 confirmed findings (0 critical, 4 high, 28 medium, 34 low). Every candidate finding survived independent verification; a split vote counts as confirmed, so the list errs towards including issues.

## 1. Summary

The core purchase path works: the audit placed cash-on-delivery, eSewa, IME Pay and bank-transfer orders as guest and as a signed-in customer, stock was reserved atomically (3 concurrent checkouts for the last unit gave exactly one 201), prices were re-read from the database, the admin state machine confirmed payments and restocked cancellations correctly, and every authorization probe (401/403/404 on other users' data, middleware bypass CVE, open-redirect, XSS in reviews) held. Card payments being absent is acceptable for a Nepali kitchenware store launching on COD and wallet confirmations. However the store cannot go live on this build: the /shop Sort select, category chips, pagination and in-page search are dead in the production build until a full reload (same-path query navigation never completes on force-dynamic pages); every image an admin uploads returns 404 because Next snapshots public/ at build time; the payment instructions shown to eSewa/IME Pay/bank customers are hard-coded demo merchant IDs (9800000000 "Demo Store", "Demo Bank" account) that nobody can change from the admin; a cancelled bank/eSewa order still tells the customer "Amount due: Rs. 2,850, complete your payment"; and anyone holding a guest order id can read that buyer's name, phone, email and address forever. On the operations side, the only brake on mass COD order spam and account creation is a rate limiter keyed on a client-controlled X-Forwarded-For header, a demoted or deleted admin keeps full admin access for up to 30 days, the seven footer links (Privacy, Terms, Returns, Contact, Shipping, FAQ, About) all 404, and AUTH_URL/NEXT_PUBLIC_APP_URL still point at localhost:3000. Most blockers are hours-to-a-couple-of-days each; fix the eleven listed blockers, re-run the browser regression for /shop sorting, and the store is a realistic "ready-after-fixes" candidate within one to two weeks of focused work.

### High (4)

#### 1. Rate limiter keys on client-controlled X-Forwarded-For, so every per-IP limit (register, checkout) is bypassable with one header

- **Where:** `lib/rate-limit.ts:44` - category: security
- **What happens:** getClientIp() returns the first value of the X-Forwarded-For header unconditionally (falling back to x-real-ip) with no trusted-proxy check. With `next start` exposed directly, or behind a proxy that appends rather than replaces the header, any caller picks a fresh 'IP' per request and receives a fresh bucket. POST /api/auth/register (5/10 min) and POST /api/checkout (10/60 s; each call creates an Order and, for manual methods, reserves stock in placeManualOrder) are keyed on this helper, so the only brake on mass account creation and stock-reserving cash-on-delivery order spam is defeated. CLAUDE.md 4.4 requires public write endpoints to be rate limited; the limit exists but is trivially defeatable.
- **How to reproduce:** Attacker's IP is at the register limit (429). They resend the identical POST with `X-Forwarded-For: 203.0.113.7` and it is processed (201/409); rotating the header yields unlimited accounts. Likewise, looping POST /api/checkout with paymentMethod CASH_ON_DELIVERY and a different X-Forwarded-For each time creates hundreds of PENDING orders, each decrementing stock, until real customers see 409 Insufficient stock and an admin cancels them one by one.
- **Evidence:** lib/rate-limit.ts:44-51: `const forwarded = request.headers.get("x-forwarded-for"); if (forwarded) { const first = forwarded.split(",")[0]?.trim(); if (first) return first; } return request.headers.get("x-real-ip") ?? "unknown";`. Call sites: app/api/auth/register/route.ts:15 `rateLimit(\`register:${getClientIp(request)}\`, RATE_LIMIT)`; app/api/checkout/route.ts:34 `rateLimit(\`checkout:${getClientIp(request)}\`, ...)`. Live on :3001: `POST /api/auth/register`-> 429 {"error":"Too many registration attempts..."}; same body with`-H "X-Forwarded-For: 203.0.113.7"`->`HTTP/1.1 409 Conflict`, `x-ratelimit-remaining: 4`; with `X-Forwarded-For: 203.0.113.77`->`{"data":{"id":"cmu2kqe3f005sv9ikst26bpfe","email":"audit-authz-1@example.com"}} [201]`. 14 POSTs to /api/checkout with distinct XFF values -> `400 x14`(never 429) vs 12 POSTs with the same spoofed header ->`400 x10 429 429`. 8 register POSTs with XFF 10.99.1.1..10.99.8.8 -> 400 x8; 7 with fixed 10.98.7.7 -> 400 x5 429 429. Two POSTs with XFF 10.9.9.1 then 10.9.9.2 both returned `x-ratelimit-remaining: 4` (new bucket each).
- **Fix:** Only honour X-Forwarded-For when a trusted reverse proxy is explicitly configured (e.g. TRUST_PROXY=true in lib/env.ts) and then take the last untrusted-hop value (or the platform header: CF-Connecting-IP, X-Vercel-Forwarded-For), never the first; otherwise key on the socket address. Add a second key dimension (email for register, session user id / email for checkout) and cap manual-method orders per email per hour. Replace the in-memory Map with Redis/Upstash before multi-instance deployment.

#### 2. Role changes and account deletions are not enforced: JWT role/identity is trusted for 30 days with no DB re-validation, so demoted or even deleted admins keep full admin access and deleted users keep a valid session

- **Where:** `lib/auth.config.ts:36` - category: authorization
- **What happens:** The jwt callback copies `id` and `role` into the token once at sign-in and the session callback reads them back with no DB lookup; session.maxAge is left at Auth.js's 30-day default. requireAdmin(), the admin layout and the middleware `authorized` callback all trust `session.user.role` from the token. Consequently (a) an admin demoted via /admin/customers (setUserRole only updates the DB row) keeps ADMIN access to every /admin page and /api/admin route until their cookie expires, (b) a deleted user's cookie continues to pass `auth()`/`requireUser()` and renders /account while mutating endpoints fail with 500 instead of 401, (c) a password change does not invalidate other devices' sessions. The action's own notice says 'The change applies at their next sign-in', which the affected user controls, not the admin.
- **How to reproduce:** Admin A demotes compromised admin B on /admin/customers. B (or whoever holds B's cookie) keeps full admin access - product edits, order status/payment changes, promoting a second account back to ADMIN - for up to 30 days; only rotating AUTH_SECRET stops it. After a user row is deleted, their cookie still yields a valid session and /account renders.
- **Evidence:** lib/auth.config.ts:11 `session: { strategy: 'jwt' }`; :36-47 `jwt({ token, user }) { if (user) { token.id = user.id ?? token.sub ?? ""; token.role = user.role; } return token; }, session({ session, token }) { session.user.id = token.id; session.user.role = token.role; return session; }` - no prisma lookup; `grep -rn "maxAge|updateAge" lib/auth.ts lib/auth.config.ts` -> no matches; @auth/core/lib/init.js:38 `const maxAge = 30 * 24 * 60 * 60`. lib/auth.ts:58-64 requireAdmin() checks session.user.role only. app/admin/customers/actions.ts:18 comment 'The role lives in the JWT, so the affected user sees the change after their next sign-in.' Live: audit user created as ADMIN, signed in -> `GET /api/admin/orders: 200`; DB role set to CUSTOMER -> same cookie: `/api/auth/session` still `"role":"ADMIN"`, `GET /api/admin/orders after demotion: 200 {"data":[...]}`, `GET /admin/customers page after demotion: 200`, `POST /api/categories after demotion: 201`. Live: signed in as reviewer.1@example.com, deleted the row (`deleted 1`), then `GET /api/auth/session` still returned `{"user":{...,"id":"cmu2k7e6g0010v9ikw7j65rpy","role":"CUSTOMER"}}`, `GET /account` -> 200, `GET /api/me` -> 404, `POST /api/addresses` -> 500 {"error":"Failed to create address"}. - **Fix:** Re-validate server-side: in requireAdmin() and the admin layout read the current role from the DB (`prisma.user.findUnique({ where: { id }, select: { role: true } })`) and refuse when not ADMIN; in the jwt callback re-read `{ role }` and a per-user `sessionVersion`/`passwordChangedAt` column when `trigger === 'update'` or when `token.checkedAt` is older than N minutes, returning null/`{}` for missing users and stale versions; bump the version on role change and password change; lower session.maxAge (e.g. 7 days, shorter for admins) and provide an admin 'sign out everywhere'.

### Medium (28)

#### 5. Credentials sign-in has no rate limit, throttle or lockout (unlimited online password guessing)

- **Where:** `lib/auth.ts:25` - category: auth
- **What happens:** Neither `signInAction` nor the Credentials `authorize()` callback applies any per-IP or per-account throttle; lib/rate-limit.ts is used only by register, checkout, reviews and change-password. Only bcrypt cost 12 (~0.35-0.4 s per guess) slows an online attack against a known email such as admin@example.com (shown in the sign-in demo hint outside production and in docs); parallel connections remove even that. There is no audit log of failed attempts. Combined with the timing-based existence leak (separate finding) this enables credential stuffing against harvested emails.
- **How to reproduce:** Attacker targets admin@example.com with a password list at 10 concurrent connections (~25 guesses/s, ~2M/day) to POST /api/auth/callback/credentials and is never blocked or slowed; a weak-but-policy-compliant admin password falls in hours.
- **Evidence:** lib/auth.ts:25-44 `async authorize(raw) { const parsed = signInSchema.safeParse(raw); ... const user = await prisma.user.findUnique(...); if (!user?.passwordHash) return null; const valid = await compare(...); ... }` - no rateLimit; app/(auth)/actions.ts:34-62 signInAction - no rateLimit. grep 'rateLimit(' over app/ and lib/ matches only app/account/profile/actions.ts, app/api/auth/register/route.ts, app/api/checkout/route.ts, app/api/products/[id]/reviews/route.ts. Live: 12 consecutive wrong passwords for admin@example.com to POST /api/auth/callback/credentials -> `200 x12`, 13th still `{"url":".../sign-in?error=CredentialsSignin&code=credentials"}`; 5 rapid wrong-password POSTs -> 200 200 200 200 200 (no 429).
- **Fix:** Add `rateLimit(\`signin:${ip}\`)` and `rateLimit(\`signin:${email}\`)`(e.g. 10/15 min) inside`authorize()` (it runs for both the Server Action and the raw callback) and return null / throw a custom AuthError mapped to 'Too many attempts'; consider progressive delay or temporary lock after N failures per account, and back the limiter with a shared store for multi-instance production.

#### 6. Registration Server Action bypasses the register rate limit entirely (CLAUDE.md 4.4)

- **Where:** `app/(auth)/actions.ts:87` - category: rule-violation
- **What happens:** Only `POST /api/auth/register` is rate limited (5/10 min per IP). - **Evidence:** app/(auth)/actions.ts imports `signIn, signOut`, `resolveCallbackUrl`, `registerUser`, schemas - no `rateLimit` import (`grep -n rateLimit app/(auth)/actions.ts` -> no matches); lines 85-91: `let result: Awaited<ReturnType<typeof registerUser>>; try { result = await registerUser(parsed.data); } ...`. components/auth/RegisterForm.tsx:19 `useActionState(registerAction, initialState)`. #### 7. AUTH_URL pins every Auth.js redirect (middleware, sign-in, forbidden) to its own origin, and lib/env.ts / RUNBOOK neither cross-check it against NEXT_PUBLIC_APP_URL nor warn that AUTH_TRUST_HOST is ignored while AUTH_URL is set - a stale AUTH_URL silently breaks login on the real host instead of failing fast at boot

## 7. What is working well

- Trust boundary at checkout holds: the client sends only productId+quantity; prices, active flag and stock are re-read from the DB and totals computed in Decimal; three concurrent guest COD checkouts for the last unit produced exactly one 201 and two 409 'Insufficient stock' (conditional updateMany inside $transaction).
- Manual-payment order lifecycle works end to end: guest and signed-in COD/eSewa/IME Pay/bank orders placed (201), stock reserved (70 -> 64), server cart emptied, payment references required only for wallet/bank methods, admin PENDING -> SHIPPED -> PAID -> DELIVERED, cancel restocks exactly once (63 -> 66, second cancel 409), Stripe orders refuse manual payment updates (409), invalid transitions 409.
- Authorization is enforced in queries, not UI: 401 for every anonymous API call, 403 for customer on every admin route/action, 404 for other users' addresses/orders, review edits owner-only; verified with a second customer account; Next 15.5.25 rejected the x-middleware-subrequest bypass (CVE-2025-29927).
- Auth hygiene: bcrypt cost 12, identical responses for wrong password / unknown email / passwordless account, sanitizeCallbackUrl rejected all 19 open-redirect variants probed (//evil.com, /\evil.com, https://evil.com, javascript:, control chars), CSRF token required for credentials/signout POSTs, HttpOnly SameSite=Lax cookie, JWT carries no password hash, demo-credential hint absent from the production build.
- Input hardening: XSS payloads in reviews and search rendered escaped; linkHrefSchema blocks javascript: and //host in admin content; product image schema rejects javascript: and /uploads/../ paths; upload endpoint sniffs magic bytes (renamed and SVG files rejected), enforces 5 MB, and uses UUID filenames; no raw Prisma queries anywhere.
- Admin-managed home content matches the database exactly: hero slides, side banner, promo tiles, announcements, trust badges, testimonials, footer columns, store info, category circles with (N items) counts, Best Sellers ranking by review count/average, New Arrivals, store-wide 4.6/5 from 83 reviews; settings saved in /admin/settings appeared on the home page immediately.
- Storefront data consistency: /shop filters, sorts, onSale (19 products, all compareAt > price), featured (5), category counts, discount percentages, Rs. formatting, JSON-LD (NPR, 4.8/9) and the sitemap (36 products + 9 categories, no inactive) all agree with the DB.
- Stripe path is safely disabled: card option hidden at checkout, POST /api/checkout STRIPE -> 503, webhook -> 503 without a secret and signature-verified with idempotent fulfilment (updateMany where paymentStatus != PAID) when configured.
- No runtime errors: 0 'Application error' markers across 44 public URLs and 23 admin pages, 0 uncaught page errors and 0 hydration/key warnings in headless Edge on desktop and mobile; localStorage-derived UI is gated by useHydrated(); root layout degrades gracefully when the DB is down.
- Address and profile invariants verified via API and UI: exactly one default address at all times, deleting the default promotes another, ownership scoped by userId, forms round-trip values on validation errors, password change verifies the current password and is rate limited per user.
- Quality gates: tsc strict passes, 556 unit tests + 17 DB integration tests pass against the live Postgres, all four migrations applied with no drift found in a manual pg-catalog comparison, every relation has an explicit onDelete matching CLAUDE.md 5.2, money stays Decimal server-side and is serialised only at the client boundary, CI runs typecheck/lint/test/build plus migrate-deploy, drift check and double seed.
- Mobile layout basics: fixed tab bar, hamburger drawer with 9 categories and body scroll lock, side banner hidden on phones, header without a location row; accessibility basics (sr-only labels, aria-pressed toggles, aria-current pagination, Escape handling) are present.

## 9. Method

Nine independent code reviewers (auth, authorization, checkout and payments, storefront, account, admin, data layer, security, operations) and eight live test suites (public pages, auth flows, account flows, checkout flows, admin flows, data consistency, real-browser checks, quality gates) ran in parallel against the code and a production build of it (next start on a dedicated port). Their findings were merged, then each was re-examined by independent verifiers told to reproduce it, refute it, and judge its impact; only findings with a majority verdict of real are reported.

Suites: Public pages smoke (28 pass / 9 fail / 0 blocked); Authentication flows (curl + headless Edge against http://localhost:3001) (16 pass / 4 fail / 0 blocked); Customer account flows (curl + Playwright against http://localhost:3001 as customer@example.com) (28 pass / 5 fail / 1 blocked); Checkout and order flows (curl against http://localhost:3001) (38 pass / 3 fail / 0 blocked); Admin flows (curl + headless Edge) against http://localhost:3001 as admin@example.com (20 pass / 6 fail / 1 blocked); Data consistency between the UI and the database (http://localhost:3001) (21 pass / 5 fail / 0 blocked); Real-browser checks (playwright-core / Edge headless) against http://localhost:3001 - desktop 1366x900 and mobile 390x844 (21 pass / 8 fail / 0 blocked); Quality gates (typecheck, lint, unit tests, DB integration tests, CI workflow parity) (7 pass / 1 fail / 0 blocked)
